# ADR-0008: 리뷰어 구성

- 날짜: 2026-10-23 (승인 2026-10-26)
- 상태: 승인
- 결정자: 팀 설계로 (#42 착수 시 R1 승인)

## 배경

검토 관점 4개(A05~A08)를 각각 노드로 만들면 통합·비용·호출 한도 부담이 크다. 하나로 합치면 관점이 섞이고 분업이 줄어든다.

## 결정

- 관점 4개는 설정 파일(프롬프트·체크리스트·입력 선택·오탐 기준)로 유지하고, 구현은 리뷰어 노드 1종으로 한다.
- 설정으로 `parallel`(4개 병렬)과 `combined`(1개에 4관점)를 바꾼다. 출력은 공통 Finding, `reviewer_id`로 관점 구분.
- 실행 방식은 같은 입력으로 비교해 결함 탐지율·오탐·토큰·시간으로 정한다. 통합이 늦으면 `combined`로 먼저 연결한다.
- 분업은 관점 설정 단위로 한다.
- 구현 세부 (#42):
  - 관점 설정은 `specton/review/perspectives/<reviewer_id>.yaml`에 둔다 (도메인과 무관한 검토 기준이므로 도메인 팩에 넣지 않는다).
  - 기본 실행 방식은 `combined`(호출 비용이 가장 적음). `SPECTON_REVIEW_MODE`로 바꾸고, 평가 후 최종 확정한다.
  - `parallel`의 관점 동시 실행은 그래프(#18)가 맡고, 리뷰어 노드는 관점 단위 함수만 제공한다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| A: 4개 노드 따로 구현 | 관점 분리 명확 | 검토 호출 4회/반복, 최악 약 36회 | 통합·비용 부담 |
| B: 1개 + 체크리스트 4개 | 호출 1회/반복, 최악 약 24회 | 관점 혼재, 분업 축소 | 관점별 평가 불가 |
| C: 2개로 묶음 | 호출 2회/반복 | 묶는 기준이 임의적 | 근거 약함 |

## 결과

- 좋아지는 점: 평가 결과에 따라 실행 방식을 코드 변경 없이 바꿀 수 있다.
- 감수할 점: 공통 리뷰어 노드를 처음에 잘 설계해야 한다.
