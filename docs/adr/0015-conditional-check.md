# ADR-0015: 추출 확인·분석 확인 조건부 진행

- 날짜: 2026-11-01
- 상태: 승인
- 결정자: #95 (의견 수렴 후 R1 결론, 2026-11-04)

## 배경

- 지금 흐름은 업로드 직후 사용자가 두 번 확인한다. UI-02 추출 확인(「필요 시 사용자 보완」, docs/03 30행)과 UI-03 분석 확인(HITL 1, A01 뒤 항상 멈춤, docs/03 32행)이다.
- 상태도에는 추출 확인 없이 바로 분석으로 가는 길(`parsing → analysing`)이 이미 있지만, 언제 멈추는지 기준은 문서에 없다(docs/03 108∼110행).
- 「사용자 보완」(사용자가 추출된 문장을 직접 고치는 것)이 결과를 얼마나 좋게 하는지 확인한 자료는 아직 없다.

## 결정

1. **조건부 확인**: UI-02·UI-03은 확인할 것이 있을 때만 멈춘다. 확인할 것이 없으면 결과를 화면에 보여 주고 다음 단계로 간다.
   - UI-02 멈춤 조건: 추출 판정이 `review`·`fail`인 원문이 있을 때.
   - UI-03 멈춤 조건: 품질 경고나 사용자 답이 필요한 질문이 있을 때, 또는 코드로 확인할 수 있는 다음 조건일 때.
     - 분할: 같은 원문(`source_ref`)에서 나온 요구사항이 2건 이상이다. 그중 FR과 NFR이 섞여 있으면 기능·비기능 분할로 따로 표시한다. #17이 A01 결과의 요구사항 수로 계산하며 새 계약 칸은 두지 않는다.
     - 원문 대조 누락: A01은 연결되지 않은 입력 블록이 하나라도 있으면 재요청하고 끝내 실패로 끝낸다. 블록 안 항목 누락은 A06과 UI-03에서 사람이 본다.
   - UI-03에서 멈추지 않으면 UI-04에 「분석 확인 생략(확인할 항목 없음)」을 표시한다 (`analysing → designing`).
2. **검증은 멈추지 않아도 그대로 돈다**: 추출 판정, A01 품질 경고, 검토 에이전트(A05∼A08), 추적 검사(`find_trace_issues`)는 건너뛰지 않는다. 사람 확인을 줄이는 대신 검증 결과를 기록으로 남긴다.
3. **추출 판정 방식**: 코드가 `pass`·`review`·`fail`을 정한다. LLM 의심 표시는 1차 범위에서 뺀다. 형식만 보고 UI-02를 건너뛰지 않으며, 엑셀도 코드 판정을 거쳐 모두 `pass`일 때만 멈추지 않는다.
   - 판정 이유는 사용자가 이해할 문구로 `SourceRequirement.notice`에 둔다. 자세한 오류는 개발용 로그에만 남긴다.
   - 요구사항명·상세 내용 칸이 모두 빈 행(범례·각주 줄 등)은 버리지 않고 원문 문장 없이(`source_text = null`) `review` 블록으로 둔다.
   - 파일 단위로 읽지 못하면(손상, 시트를 읽지 못함, 요구사항 표를 찾지 못함, 파일 전체가 빈 양식 등) 실행 중에 걸러 `EXTRACTION_FAILED`로 끝낸다. 받지 않는 확장자는 `POST /runs`에서 415다.
   - 일부 시트만 비었거나 머리글을 찾지 못해 건너뛴 시트는 안내만 하고 확인·제외 대상으로 두지 않는다.
   - `fail` 판정 기준은 #24에서 HWP·HWPX를 시험한 뒤 정한다. 그때까지 `fail` 값과 아래 처리 규칙은 그대로 둔다.
4. **재추출**: 보류. 지금은 대상이 없다(PDF는 범위 밖). HWPX는 #24 시험 뒤 필요하면 다시 연다.
5. **UI-02는 문장을 고치지 않고 확인 또는 제외만 한다.** 결정은 블록마다 `SourceRequirement.user_decision`(`confirmed`·`excluded`)에 두고, 노드는 제외한 블록과 원문 문장이 없는 블록을 분석하지 않는다.

   | 판정 | 확인 | 제외 | 제외 사유 | RTM |
   |---|---|---|---|---|
   | `pass` | 묻지 않음 | 불가 | — | 원문 → 요구사항 → 기능·엔티티 |
   | `review` | 가능 | 가능 | 필수 | 확인: 원문이 있으면 분석, 없으면 「확인(원문 없음)」 행. 제외: 「제외」 행과 사유 |
   | `fail` | 불가 | 필수(남기면 진행 불가) | 선택 (없으면 판정 이유) | 「제외」 행과 사유 |

   - `ExtractionResponse`는 `edits`를 빼고 `excluded_blocks`(`block_id`, `reason` 선택)를 둔다. `confirmed=false`는 중단(`cancelled`)이다. 위 표를 어기면 422 `INVALID_RESPONSE`다 (06 문서).
   - 제외 후 남은 블록이 0건이면 `EXTRACTION_FAILED`다.
   - 제외하는 원문의 `source_id`가 남은 원문의 `source_related_requirements`에 나오면 UI-02에서 경고하고 `run_event`에 기록한다. 제외는 막지 않는다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| A. 지금대로: UI-02 사용자 보완 + UI-03 항상 멈춤 | 사람이 모든 단계를 본다 | 업로드 직후 두 번 확인. 문제가 없는 문서도 멈춘다 | 확인 부담이 크다 |
| B. 조건부 확인 + 검증 유지 (이 제안) | 문제가 있는 건만 사람이 본다 | 경고 없이 넘어간 분류·분할 오류는 뒤 단계에서 잡아야 한다 | — |
| C. 확인 단계 모두 없앰 | 가장 빠르다 | 추출 실패를 사람이 볼 기회가 없다 | 추출 실패는 분석으로 넘기면 안 된다(docs/11 40행) |

## 결과

- 좋아지는 점: 문제가 없는 문서는 사람 확인 없이 설계까지 간다. 사람은 `review`·`fail` 건과 경고가 있는 건만 본다. 원문에 있던 줄은 제외하거나 원문이 없어도 RTM에 남아 조용히 사라지지 않는다.
- 감수할 점: 경고 없이 넘어간 분류·분할 오류는 검토 에이전트와 HITL 2(UI-06)에서 잡아야 한다. 멈춤 조건이 맞는지 평가 세트로 시험해야 한다(R2).
