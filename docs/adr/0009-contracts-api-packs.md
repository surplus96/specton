# ADR-0009: 데이터 계약·API·도메인 팩 형식

- 날짜: 2026-10-23 (계약 승인 2026-10-26)
- 상태: 계약 승인, 재고·공통 도메인 팩 결정 (2026-11-09, #11)
- 결정자: 팀 설계로 (계약은 PR #48 리뷰에서 R1 승인, 팩은 #11에서 결정)

## 업무 키·FK 선언 보완 (#290)

- 복합 업무 UNIQUE는 EntityDraft.unique_keys의 속성 이름 묶음으로 받고 저장 시 Entity.unique_keys의
  속성 ID 묶음으로 바꾼다. 개별 is_unique와 다르며 대리키와 함께 유지할 수 있다.
- FK 재사용은 A04가 fk_bindings에 부모의 직접 PK 속성·자식의 기존 업무 속성을 명시한 경우만
  허용한다. 이름·타입으로 추측하지 않고, 타입·NULL·키 참조가 맞지 않으면 RULE-04로 재작업한다.
  N:M 연결 테이블·상속된 부모 키의 재사용은 이 첫 범위에 넣지 않는다.
- 재사용 컬럼은 원래 속성 출처를 유지하고 FK 객체가 참조 쌍을 기록한다. 같은 컬럼이 식별 관계와
  자기 키에 함께 포함되더라도 PK에 중복하지 않는다. 미선언은 기존 D13 동작을 유지한다.
- 새 필드가 없는 옛 설계 해시는 유지한다. normalize-v3·A03/A04 v4의 새 실행에서 검증하고,
  옛 승인본을 바꿔 이어 쓰지 않는다. 선언한 제약은 SQL로 검증하지만 선언 누락의 의미 판정은
  기존 검토 관점·HITL 책임이다.

## 운영 사전 출처 검증 보완 (2026-11-10, #291)

- inventory 0.1.23은 #299에서 승인한 개발용 단어 4개의 원본 사본·선정 사유를 고정한다.
  0.1.21 기준 사전과 다른 모든 단어를 검증하며, 새 평가 관측 이름은 추가하지 않는다.
- manifest.lexicon_sources는 선택 필드이며 기존 팩을 호환한다. 선언한 출처는 build·loader·
  명명 함수에서 검증하고 정책 해시에 원본 바이트를 포함한다. 상세 형식은 docs/10을 따른다.
- 운영 확장과 평가 전용 A08 탐색 사본을 구분한다. 외부 출처가 있다는 사실만으로 선정 독립성이나
  블라인드 평가를 주장하지 않는다. 실제 조건별 평가는 #20에 남기고 기존 결과·해시는 보존한다.
- R1·R4의 의미·선정 검토는 코드 검증과 별개다. 출처 확보·기계 검증을 사람 승인으로 기록하지
  않으며 검토 완료 전 최종 릴리스 판정을 내리지 않는다.

## 배경

에이전트 담당 5명이 같은 계약을 쓰므로 먼저 동결해야 병렬 구현이 가능하다. 도메인 팩은 공공데이터 공통표준 8차(2025-11)로 초안을 만들었고 형식 결정이 남아 있다.

## 명명 지원 보완 (2026-11-10, #20)

- 추가 검토: common 0.1.7·normalize-v2는 공식 원본의 비모호 이음동의어만 명명 조합에
  허용한다(`term.word_aliases=official_unambiguous`). 금칙어·모호한 표준어 연결·기존
  등록 이름 덮어쓰기는 제외한다. SC-04 진단과 원래 논리명은 유지한다.
- 대리키 변경 시 기존 복합 업무 키의 유일성이 보존되는지 별도 확인한다. 당시 Entity 계약은
  복합 업무 UNIQUE를 직접 표현하지 못했다(#290에서 보완). 필요한 조합 유일성을 잃는 대리키 설계를 승인하거나
  구성 속성 각각의 전역 UNIQUE로 대체하지 않는다. 계약 확장이 필요하면 별도 변경으로 다룬다.

- common 0.1.6은 같은 고정 원본의 활성 단어 전체를 명명 사전에 포함한다. inventory 0.1.21과
  평가 정답은 유지한다. 변경 전 고정 판은 아래 2026-11-09 결정 표에 남긴다.
- 반복 FK의 `relationship_id` 명명은 같은 부모·자식의 1:1/1:N에만 적용한다. 다른 부모의
  키 충돌(D4)은 사람 조치, 기존 업무 속성과의 충돌(D13)은 설계 재작업이다. 이름·타입만으로
  FK를 합치거나 자식의 키를 지우지 않는다.
- 사전에 없는 이름은 RULE-05·critical·사람 조치로 유지한다. 같은 의미의 등록 표현을 사람이
  확인하거나 출처·약어를 검토해 새 팩 판으로 등록한다. 임의 번역·자동 약어로 통과시키지 않는다.
- 사람 조치 전에 A03이 한 번만 이름을 다시 본다(#291, a03-v5). 사전으로 물리명을 만들 수 없는
  엔티티·속성 이름만 모아 「뜻이 같은 표준 표현이 있으면 바꾸고, 없으면 그대로 둔다」로 재요청한다.
  사전·약어·평가 관측 이름은 넣지 않는다. 이름 말고 구성이 바뀐 응답은 버리고, 그래도 남은 이름은
  위와 같이 RULE-05·critical·사람 조치다. 바뀐 이름은 최종 검토에서 사람이 확인한다.
- inventory 0.1.22(#291)는 공통표준에 없는 낱말 4개(간선·금형·거점·연차)를 더한다. 개발용 합성 세트
  실제 실행에서 풀리지 않던 낱말이고, 약어·영문명은 공공데이터포털의 이용허락범위 제한 없는 공공기관
  표준사전 값이다(출처는 `inventory/words.yaml` 머리 주석). 평가 세트에서 본 낱말은 넣지 않았다.
  0.1.21로 한 실행·승인·해시는 그대로 두고, 0.1.22는 새 실행에만 적용한다.
- 평가 관측에서 얻은 이름을 팩·프롬프트에 추가하는 적응 작업은 고정 평가와 분리한다.
  현재 보완에는 그런 이름·정답을 넣지 않으며, 기존 실행·승인 해시를 교체하지 않는다.
- A03·A04 재작업 입력에는 직전 엔티티·관계와 검토 지적을 넣는다(a03-v3·a04-v3).
  지적의 대상 ID는 위치 확인용이며 출력 ID는 계속 코드가 생성한다. 지원 부족을 해결하려고
  업무 관계를 없애지 않는다. 사람 조치가 섞이면 기존대로 자동 재작업보다 HITL을 우선한다.

## 결정

### 계약 (승인)

- [05 데이터 계약](../05-data-contracts.md), [06 API](../06-api.md), [api/openapi.json](../api/openapi.json)을 기준으로 계약을 동결한다. ADR-0006을 반영한다. PR #48 병합 시점이 동결 시점이다.
- `source_ref`는 **구조체**(`file_format`별 `sheet`/`row`/`page`/`block`/`section`/`paragraph`/`table`/`cell`)다. 행·쪽은 1부터, 블록·구역·문단·표는 0부터 센다. 화면 표기는 코드가 만든다.
- 계약 구현은 `specton/contracts/`의 Pydantic 모델이며 LLM 출력(`*Draft`)과 저장 모델을 나눈다. 모든 계약 모델은 불변(`frozen`)이고 목록 필드는 튜플이다. 값을 바꿀 때는 검증을 다시 거치는 `evolve`를 쓴다.
- 속성 제약 표현(`check`)은 계약에 두지 않는다. 중복 금지만 `is_unique`로 두고, 값 범위 등 허용 범위는 규칙 검사(#15)에서 정한 뒤 추가한다.
- 오류 코드는 06 문서의 17개다. 실행 실패 원인(`LLM_REFUSED`·`LLM_OUTPUT_INVALID`·`LLM_UNAVAILABLE`·`BUDGET_EXCEEDED`·`EXTRACTION_FAILED`)을 `INTERNAL`과 구분한다.
- 동결 후 계약 변경은 `contract-change` 라벨과 2인 승인(R1 + 계약 영향을 받는 담당 1명)을 거친다. R1이 작성한 변경은 R1 자체 점검 기록으로 승인을 대신한다 ([CONTRIBUTING](../../CONTRIBUTING.md#리뷰)).
- 계약 변경 확인은 R2가 맡는다. `contract-change` PR의 의미·문서·테스트를 확인해 코멘트한다. 계약 주관은 R3이다.

### 도메인 팩 (승인 기준, #11)

| 항목 | 결정 |
|---|---|
| 현재 범위 | 재고 + 공통. 설비는 현재 구현 완료·평가 기준에서 제외하고 기존 파일은 유지 |
| 타입 프로필 | `strict` (일자 char(8), 여부 char(1) Y/N). `pg_native`는 명시적 대안이며 실행 중 교체하지 않음 |
| 조합 코드 길이 | 재고 업무 코드 `코드C10`, 유형·상태 `코드C2` (개발 요구사항 기준) |
| 공유 용어·패턴 | 단어·도메인·명명·검사 정책은 common. 사용여부·변경일시·변경사유와 사용 중지 패턴은 도메인 용어·패턴에 유지. 실행기가 읽지 않는 `common/terms.yaml`·`common/patterns.yaml` 신설·이동 제안은 채택하지 않음 |
| 명명 | 단어 수 제한 없음, 접두어 없음, 사전 약어 그대로, 연결 테이블 parent_child, PK 용어 물리명, FK 부모 키, 자기참조 접두어 상위(UP) |
| 규칙 처리 | `handling`: fixed(고정 복귀) / dynamic(대상·문제별 계산) / manual(사람 조치) / informational(minor 참고). fixed만 target_stage를 채우며, 나머지 null은 확정된 값 |
| SC 세부 유형 | SC-04 기본은 금칙어 major·manual, `subtypes.synonym`은 minor·informational. 팩에 없는 공식 이음동의어 진단은 #260에서 추가(common 0.1.5) |
| 선별 적용 | `standard_selection.yaml`에 낱말·표준어·사유를 기록. 목록에 없는 공식 이음동의어·금칙어 등록, 빈 사유, 잘못된 표준어, 남은 예외는 로더·build 검사가 거절 |
| 공통표준 판 | 8차 CSV와 `sources.yaml` sha256 고정. 9차를 자동 도입하지 않음 |
| 버전 고정 | common 0.1.5 approved (#260), inventory 0.1.21 approved. 각 내용·선별 적용을 pack.lock에 기록. 정리 결과에 common_version·policy_digest를 보존하고 모델 해시·manifest에 포함 |
| 재개 | 정리 후 팩·표준 원본 해시가 다르면 새 실행을 요구. 옛 결과에 없는 새 메타데이터를 채워 옛 승인 해시를 바꾸지 않음 |
| 평가 자료 | 비공개 보관, 팩·프롬프트·공개 저장소에 입력하지 않음. R1이 정답 검토와 R2 팩 후속을 겸하므로 작성자 미열람 평가로 주장하지 않으며 이 제한을 평가 기록에 남김 |
| 형식·인수 | Pydantic·정책·선별 적용·내용 해시 검증. R2 잔여는 R1이 인수, 계약 영향은 R3 확인 대상 |

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 계약 없이 각자 구현 후 통합 | 초기 속도 | 통합 시 대규모 수정 | 병렬 개발 불가 |

## 결과

- 좋아지는 점: 모든 에이전트를 고정 응답으로 동시에 개발할 수 있다.
- 감수할 점: 동결 후 계약 변경은 `contract-change` 라벨과 2인 승인(R1 작성 변경은 예외 절차), R2의 변경 확인이 필요하다.
