# ADR-0016: 모델 정리의 내부 ID와 키 없는 엔티티

- 날짜: 2026-11-05
- 상태: 제안
- 결정자: R4 (#129 리뷰에서 R1이 #12·A03 범위로 R4 판단에 맡김)

## 배경

모델 정리(#12)는 A03 엔티티·속성과 A04 관계를 테이블·컬럼·PK·FK로 바꾼다. 두 가지를 정해야 한다.

1. 결과의 ID를 무엇으로 만드는가. 재작업 전후를 비교하거나 승인본을 다시 만들 때 기준이 된다.
2. PK가 없는 엔티티를 어떻게 처리하는가. 이 프로젝트는 최종 PK가 없는 설계를 규칙 위반으로 막는다(RULE-03).

지금 ID는 이렇게 만들어진다.

| 대상 | 만드는 곳 | 방식 | 재작업 뒤 |
|---|---|---|---|
| 엔티티·속성 | A03 | 팩·이름의 해시 (`ENT-…`, `ATTR-…`) | 이름이 같으면 같은 ID |
| 기능 | A02 | 순번 (`FUNC-01`…) | 번호가 바뀔 수 있음 |
| 관계 | A04 | 순번 (`REL-01`…) | 번호가 바뀔 수 있음 |
| 테이블·컬럼·FK | 모델 정리 | 원래 엔티티·속성·관계 ID의 해시 | 원래 ID를 따라감 |

## 결정

### 1. 내부 ID

| 대상 | 결정 |
|---|---|
| 엔티티·속성 | 지금처럼 이름으로 만든다. 이름이 바뀌면 다른 대상으로 본다. |
| 테이블·컬럼·FK | 원래 엔티티·속성·관계 ID로 만든다. 같은 입력이면 같은 ID가 나온다. |
| 기능·관계 | 순번 방식을 바꾸지 않는다(A02·A04 코드 변경 없음). |

- **재작업 전후의 기능·관계는 짝을 맞추지 않는다.** 재작업 결과 전체를 새 설계로 본다.
- **승인본은 번호가 아니라 저장된 정리 결과로 확인한다.** 저장 방식은 #129 리뷰의 R3 제안을 따른다. 정리 결과를 `DesignState.normalized`에 담아 스냅샷에 저장·해시하고, 재작업하면 비우고 다시 채운다.
- **관계는 부모·자식 쌍만으로 구분하지 않는다.** 같은 두 엔티티 사이에도 다른 관계가 있을 수 있다(예: 출발 창고·도착 창고).

### 2. 키 없는 엔티티

| 항목 | 결정 |
|---|---|
| 판단 시점 | 식별 관계로 부모 키를 물려받은 뒤에도 PK가 없으면 |
| 처리 | 정리를 막고 `no_primary_key`로 보고한다. 설계 재작업으로 보낸다(규칙 코드·심각도는 #15). |
| 대리 키 | 코드가 일련번호 등을 자동으로 붙이지 않는다. 무엇으로 행을 구분할지는 설계 판단이다. |
| A03 | 모든 엔티티에 자기 키를 강제하지 않는다. 부모 키를 물려받아 PK가 완성되는 자식이 있다. |
| 이어지는 문제 | PK 없는 엔티티를 부모로 둔 관계는 따로 보고하지 않는다. 원인이 같다. |

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 관계 ID를 부모·자식으로 계산 | 같은 쌍에 관계가 둘 이상이면 ID가 겹친다. |
| 기능·관계 ID를 지금 해시로 바꿈 | A02·A04의 ID 부여 방식과 관련 테스트를 바꿔야 하고, 같은 대상으로 볼 기준이 먼저 필요하다. 구분 정보를 새로 담으면 계약 변경도 필요하다. |
| 키 없는 엔티티에 대리 키 자동 추가 | 행 구분 기준 없이 키가 생겨 중복 데이터를 막지 못한다. |
| A03에서 모든 엔티티에 자기 키 강제 | 부모 키를 물려받는 자식과 충돌한다. A03은 FK 속성을 넣지 않는다. |

## 결과

**좋아지는 점**

- 같은 입력이면 같은 ID가 나와 결과를 비교·재현할 수 있다.
- 키 문제는 원인 하나로 보고되어 무엇을 고칠지 분명하다.

**감수할 점**

| 영향 | 내용 |
|---|---|
| 반복 지적 판단 | 재작업으로 번호가 바뀐 기능·관계는 지문 비교(`review/rework.py`)에서 다른 대상으로 보인다. 팩·이름이 그대로이고 지적 대상이 엔티티·속성뿐이면 순번 변경의 영향을 받지 않는다. 한 지적에 관계가 함께 들어가면 관계 ID가 바뀌어 지문도 바뀐다. |
| 빗나가는 두 경우 | 반복을 놓쳐 재작업을 한 번 더 하거나, 반대로 일찍 HITL 2로 넘어간다. 반복 지적으로 판단되면 상한에 닿기 전에도 HITL 2로 넘어갈 수 있다. 반복을 놓치더라도 자동 재작업은 설정된 상한(`max_rework_iterations`, 기본 3)을 넘지 않는다. |
| 파생 ID | 관계 번호가 바뀌면 그 관계에서 만든 FK·연결 테이블 ID도 바뀐다. |
| 키 없는 설계 | 재작업 전까지 DDL·ERD·RTM을 만들 수 없다. |

**공유·후속**

- 공유: 기능(A02) 담당 R3은 승인본을 저장된 정리 결과로 확인하므로 RTM 등 산출물에 문제가 없다는 의견이다. 관계(A04) 담당 R5에게도 공유한다.
- 추후 검토: 반복 판단이 자주 빗나가면 관계도 고정 ID로 바꾸는 것을 검토한다(R3 제안: 부모·자식·카디널리티 기준). 출발·도착 창고처럼 같은 조합이 둘 이상일 수 있어 역할 이름 같은 구분 값이 함께 필요하다.
- 후속: `stable_id`를 A03과 모델 정리가 함께 쓰는 위치로 옮긴다(#137).
