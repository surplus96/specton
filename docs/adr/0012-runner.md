# ADR-0012: 실행기 구조

- 날짜: 2026-10-23
- 상태: 승인 (2026-11-02)
- 결정자: 팀 설계로 (#96 의견 수렴 후 R1 승인)

## 배경

설계 실행은 길고 HITL에서 멈췄다가 재개된다. API 요청 스레드에서 동기로 실행하면 안 된다.

## 결정

- API 프로세스 안의 백그라운드 작업으로 실행하고, LangGraph Postgres 체크포인터로 상태를 저장한다.
- 영속 run 레코드와 작업 lease로 run당 실행자를 1개로 제한한다. 프로세스가 죽으면 lease 만료 후 마지막 체크포인트에서 재개한다.
- 외부 메시지 큐는 두지 않는다.
- 배포 전제: 서버 1대, API 프로세스 1개(`--workers 1`). ADR-0013과 함께 본다.

### 실행

- `BackgroundTasks` 대신 전용 스레드 풀에서 실행한다. 동시 실행 수는 설정값(시작값 2)이고, 넘치는 실행은 `queued`로 기다린다.
- 실행기는 시작할 때 한 번, 이후 주기적으로 `queued`와 lease가 만료된 run을 찾는다.
- 추출을 별도 프로세스로 나눌지는 Excel·CSV와 HWPX 실측으로 정한다 (PDF는 이번 범위 밖).

### lease

- 만료 60초, 노드와 별개로 20초마다 갱신한다(시작값). 노드 단위로만 갱신하면 긴 LLM 호출 중 만료되어 실행자가 둘이 될 수 있다.
- 저장할 때 `holder`를 확인해 lease를 잃은 실행자의 기록을 거절한다.
- HITL 대기 중에는 lease를 반납하고, `resume` 때 다시 잡는다.

### 저장과 재개

- 재개 위치는 체크포인트, 화면에 보이는 상태와 `revision`은 `run`을 기준으로 한다.
- 노드는 상태만 반환하고 DB에 쓰지 않는다. 앱 저장은 노드가 끝난 뒤 실행기가 한다.
- run 상태·`revision`·`run_event`·`holder` 확인은 한 트랜잭션으로 묶는다. 체크포인트와는 한 트랜잭션이 될 수 없으므로 앱 저장은 멱등하게 만든다.
- 시작할 때 체크포인트가 앱 저장보다 앞서 있으면 그 지점의 앱 저장을 다시 수행해 맞춘다. 맞출 수 없으면 `failed`로 기록한다.
- LangGraph는 재개할 때 노드를 처음부터 다시 실행한다. interrupt는 LLM 호출이 없는 전용 노드에만 둔다.
- `thread_id`는 `run_id`다. 실행 삭제(ADR-0011)도 이 값으로 처리한다.

### DB 연결

- LLM 호출 중에는 DB 연결과 트랜잭션을 잡지 않는다.
- SSE는 스트림이 열려 있는 동안 연결을 계속 점유하지 않는다.
- 연결 풀 크기는 동시 실행 수, lease 갱신, API 요청을 합쳐 잡고 설정값으로 둔다.

### 취소

- 실행 중이면 API가 `cancel_requested`와 status 이벤트를 한 트랜잭션으로 남기고, 실행기가 노드 경계에서 확인해 끝낸다. 진행 중인 LLM 호출은 타임아웃까지 기다리고 그 결과는 완료본으로 올리지 않는다.
- `queued`와 HITL 대기 중에는 실행자가 없으므로 API가 run 행을 잠그고 바로 `cancelled`로 끝내고 `cancelled` 이벤트를 보낸다.

### 담당

- `job_lease` 표와 함수(잡기·갱신·반납, 재개 대상 조회, `holder` 확인): R3 (#16)
- 실행기 루프와 재개: R1 (#17)

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| Celery 등 외부 큐 | 확장성 | 구성·운영 부담 | 시연 규모에 과함 |
| 요청 안에서 동기 실행 | 단순 | 타임아웃·재개 불가 | 요구사항 위반 |

## 결과

- 좋아지는 점: 구성이 단순하고 재개가 된다.
- 감수할 점: API 프로세스를 재시작하면 진행 중 작업이 lease 만료까지 멈춘다.
