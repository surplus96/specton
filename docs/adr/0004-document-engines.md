# ADR-0004: 문서 엔진

- 날짜: 2026-10-23 (PDF 출력 승인 2026-11-08, HWP·HWPX 엔진 채택 2026-11-08)
- 상태: PDF 출력 승인, HWP 5.0·HWPX 읽기·위치 추출 엔진 채택(2026-11-08), PDF 추출·OCR 제안
- 결정자: 팀 설계로 (PDF 출력은 #13 실측과 PR 리뷰에서 R1 승인, 추출은 회의에서 결정). HWP·HWPX 엔진은 #188 댓글(2026-11-08 15:27 KST, R1)에 「HWP 5.0·HWPX의 읽기·위치 추출 엔진으로 `rhwp-python==0.8.1`을 채택하겠습니다」로 적힘

## 배경

초기 제안(2026-10-23)에서는 PDF 입력·추출, 최종 PDF 출력, HWPX/HWP 추출 후보를 공개 자료로 비교했다. PDF 출력은 아래 R5 실측과 R1 결정을 바탕으로 승인하고, HWP·HWPX 엔진은 아래 「HWP·HWPX 채택」에서 채택하며, PDF 추출 엔진은 제안 상태로 남긴다.

## 결정

- PDF 추출: Docling(표 구조 인식·OCR 내장). 텍스트형이 느리면 pdfplumber로 보조.
- PDF 출력 (승인, #13 실측 2026-11-05·11-08): 공용 엔진 하나로 기능 명세서(Markdown, #14)와 ERD(Mermaid, #13)를 PDF로 바꾼다.
  - 엔진: WeasyPrint(HTML/CSS → PDF) + `mermaid-cli`로 ERD를 SVG로 그려 넣는다. Mermaid는 웹과 같은 11.17.2로 고정한다(#13, #190, #211·#212 검토). mermaid-cli는 이미지 태그가 아니라 안의 mermaid 버전으로 맞춘다: `minlag/mermaid-cli:11.16.1`(`sha256:d98fe54c22e78e65335589fc17d5419f698f915cebca48ea21fee633aff8b258`)에 mermaid-cli 11.16.0과 mermaid 11.17.2가 들어 있다. ERD가 깨지면 Playwright 인쇄로 전환한다.
  - 한글 폰트: Noto Sans CJK KR(`fonts-noto-cjk`)을 실행 이미지에 넣고 PDF에 내장한다.
  - 렌더러는 외부 경로·URL 리소스를 가져오지 않는다. 엔진이 만든 SVG·스타일만 쓴다 (docs/10).
  - Mermaid 설정 보안 (#190 R1 리뷰): 설정은 개발자가 정한 값만 넘기고, `secure` 목록에 `themeCSS`·`fontFamily`·`altFontFamily`·`themeVariables`·`layout` 등을 넣어 원문 지시문으로 바꾸지 못하게 한다. 이름 안 지시문이 렌더 설정으로 실행되지 않도록 처리하고, ERD 외 다이어그램과 임의 원문은 그리지 않는다. 설정 변경 차단·지시문 처리·외부 리소스 차단은 PDF 엔진 PR에서 구현하고 회귀 시험한다.
  - ERD 구성: 전체 관계 개요(속성 없음) + 업무 영역별 상세도 + 테이블 정의서(전체 속성). 상세도에는 키 속성(PK·FK·UK)만 그리고 `direction LR`로 배치한다. 상세도 글자가 인쇄 용지에서 6pt보다 작으면 그 영역을 더 나누도록 경고한다. 전체 관계 개요는 전체 구조 확인용으로 나누지 않고, 6pt보다 작으면 세부는 영역 상세도에서 보라고 경고만 한다 (#236 R1 결정). 개요도 관계 이름(`REL-xx`)을 쓰고 ELK 배치(`layout: elk`, mermaid-cli에 든 `@mermaid-js/layout-elk`)로 그린다. 상세도는 기본 배치(dagre) 그대로다. 기본 배치는 긴 관계선 두 개가 가운데에서 교차하면 두 이름을 같은 자리에 둬 한쪽이 가려진다(#261). 처음에는 개요에서 이름을 빼서 막았고(#269), 그 뒤 ELK로 이름을 되살렸다(아래 「개요 ELK 재실측」). 웹 화면(mermaid JS)은 기본 배치 그대로다. 다른 영역의 참조 상자를 포함한 상자 약 13개는 실측 참고값이며, 실제 인쇄 글자 크기로 판단한다.
  - 쪽: 용지 크기는 297×210mm. 표지·긴 표는 세로, ERD·넓은 표는 가로. 긴 표는 쪽마다 머리글을 반복한다.
  - 넓은 표(예: CRUD): 기능 ID 1열 + 엔티티 20열까지 가로 한 장에 둔다. 넘으면 엔티티 열을 20개씩 나누고 각 표에 기능 ID를 반복한다. 글자를 줄여 맞추지 않는다.
  - 기능 명세서 PDF (#13): #213 Markdown을 입력으로 쓴다. Markdown 라이브러리 없이 합의한 문법(제목·문단·글머리표·굵게·인라인 코드·파이프 표·역슬래시 이스케이프)만 HTML로 바꾸고(`specton/export/markdown.py`), 그 밖의 문법은 글자 그대로 보인다. 6열이 넘는 표(CRUD 매트릭스)는 가로 쪽에 두고 위 넓은 표 규칙으로 나눈다. 진입점은 `render_function_spec_pdf(markdown, cover, draft=…)`이며, 저장·승인·manifest·다운로드는 R1(#17)이 문서 생성 가지에 ERD와 같은 방식으로 연결했다(`SPECTON_ENABLE_FUNCTION_SPEC_PDF`, docs/03).
  - 초안: 시험·내부 렌더링 검증용 초안 PDF에는 쪽마다 「초안 · 승인 전 · revision N」과 배경 표식을 넣는다. 최종 PDF는 승인한 revision에서만 만들고, 공개 PDF 다운로드도 승인본만 허용한다 (docs/06).
  - 구현 순서·분담: 이 결정 PR(#197) 병합 → R5 의존성 단독 PR → R5 공용 PDF 엔진·키 표시 옵션·영역별 출력·표 분할·보안 및 재현 시험 → R1 #17의 생성 호출·저장·산출물 인계·다운로드/내보내기 연결과 통합 검증.
- HWP 5.0·HWPX 읽기·위치 추출: `rhwp-python==0.8.1`(MIT)로 채택한다(2026-11-08). .hwp를 HWPX로 바꾸지 않고 바로 읽고, 문단마다 구역·문단 번호, 표 칸마다 행·열·병합 범위를 준다. 같은 문서의 .hwp와 .hwpx에서 구역·문단 번호가 같았다(공공 과업지시서 1건에서 확인).
  - 쪽 번호는 렌더링으로 계산한 값이라 긴 문서에서 한글 프로그램과 달라진다. 원문 위치는 구역·문단·표·셀로 적고, 렌더링 쪽 번호를 원문 쪽 번호로 쓰지 않는다. 사람용 위치 표기에는 원문 고유번호와 표 위치를 쓴다.
  - 처음 제안한 `python-hwpx`(HWPX만)와 `hwp-hwpx-parser`·`hwpkit`(HWP 5.0 표 비교)는 이번 채택 대상이 아니다. 이유는 「HWP·HWPX 채택」.
- 스캔 PDF OCR 포함 여부는 회의에서 정한다.
- 채택 전 대표 문서 2~3건으로 1시간 실측한다. HWP·HWPX는 채택 전에 실측했다(아래 「HWP 실측」).

**PDF 출력 실측 (2026-11-08, R5, #13)**

아래 수치는 R5의 실측 보고다. 동일 조건을 재현하는 스크립트·테스트는 후속 PDF 엔진 PR에 포함한다.

환경: Docker의 WeasyPrint 70.0(Python 3.12-slim, Pango, `fonts-noto-cjk`)과 `minlag/mermaid-cli:11.15.0`(안의 mermaid도 11.15.0). ERD 원문은 main의 실제 코드(`normalize_design` → `render_erd`·`render_area_erd`, #177·#182)로 만들었다. 시험 모델은 재고 팩 용어로 만든 설계를 실제 정리 코드에 통과시킨 테이블 20 · 컬럼 86 · FK 25 · 관계 24(N:M 1)이고, 영역은 기준정보 7 · 수불 7 · 재고 이력 6이다. 2026-11-05에 샘플 모델로 한 사전 실측(한글 폰트, 긴 표, 초안 표시 통과, #13 댓글)을 실제 코드 출력으로 다시 확인했다.

재실측 (2026-11-09, #211·#212 검토): PDF 엔진 시험 모델(`tests/unit/test_pdf_engine.py`, 테이블 8 · 관계 6 · 영역 3)의 원문 4개를 `minlag/mermaid-cli:11.15.0`(mermaid 11.15.0)과 `minlag/mermaid-cli:11.16.1`(mermaid 11.17.2)에서 같은 설정(`MERMAID_CONFIG`)으로 그려 비교했다. 4개 모두 오류 없이 viewBox 크기·엔티티·관계 라벨·한글 표기가 같았고, 자기참조 관계 고리만 길게 늘어진 고리에서 엔티티 아래 작은 고리로 바뀌었다. 속성 이름 글자 규칙과 단독 키워드도 같다(11.17.2는 `.`·`,`를 더 받지만 생성 코드는 쓰지 않는다). PDF 배율은 SVG viewBox로 정하므로 viewBox가 같으면 아래 글자 크기도 같다. 위 20테이블 모델과 PDF 전체는 다시 만들지 않았다.

- 개요 글자는 모델 모양에 달려 있다. 이 모델은 품목(자식 8)·창고(자식 6)에 자식이 몰려 개요가 가로로 넓다(4.5pt). 배치 방향을 바꿔도 좋아지지 않았다(`LR` 3.3pt). 이 실측 뒤 개요에도 6pt 경고를 더했다(개요는 나누지 않음, #236 R1 결정). 이 모델은 개요·기준정보 상세도 두 곳에서 경고가 난다. 개요에서 관계 이름을 뺀 뒤(#261) 같은 모델의 개요는 2459×756px · 5.0pt가 됐고(이름이 있을 때 2741×868px · 4.5pt, REL-04·REL-05 겹침), 상세도 4장은 그대로이며 이름 겹침이 없다. 이름을 되살려 ELK로 그린 뒤에는 1571×988px · 7.9pt로 6pt 경고가 없어졌다(아래 재실측).
- 상세도 6pt 경고는 기대대로 기준정보 한 곳에서만 났다(다른 영역 참조 상자가 많아 상자 16개).

- 상세도까지 ELK로 바꾸면 수불 상세도가 6pt 아래로 내려가 경고가 새로 나므로 개요만 ELK로 그린다. 이 모델의 경고는 기준정보 상세도 한 곳이 된다.
- ELK는 선을 직각으로 꺾어 그리고, 같은 자식으로 가는 선 몇 개가 한 통로를 함께 지날 수 있다. 어느 선인지는 끝 기호와 이름으로 구분된다.
- 그림 한 장 시간은 0.5초 → 0.8초 안팎(컨테이너 안 mmdc 호출, 실행 시작 포함)이다.
- 재현: `test_real_mermaid_cli_keeps_crossing_relationship_names_apart_with_elk`(교차 개요, ELK 이름 겹침 0)와 `test_pdf_scale.py`(개요 이름 25개·겹침 0·6pt 이상, 경고는 기준정보만). 둘 다 mmdc가 있는 실행 이미지에서 돈다.

## HWP·HWPX 채택 (2026-11-08)

- 결정: HWP 5.0·HWPX의 읽기·위치 추출 엔진으로 `rhwp-python==0.8.1`을 쓴다. 의존성은 #188, 파서는 #24에서 연결한다.
- 근거:
  - 한 엔진으로 .hwp와 .hwpx를 모두 읽고, 원문 위치(구역·문단·표·칸 행·열·병합 범위)를 준다. 위치 추출까지 실측한 후보는 rhwp-python뿐이다. `hwp-hwpx-parser`는 위치를 주지 않았고, `hwpkit`은 표 안 문단까지 이어 세어 문단 번호가 달라졌다(위 「HWP 실측」). `python-hwpx`는 HWP 5.0을 읽지 못하고 위치 제공은 실측하지 않았다.
  - 요구사항 상세표 양식의 공공 RFP 3건에서 요구사항 건수가 원문과 같았고(141·41·64건), 글자는 원문 XML(1건, 전수)과 다른 엔진(pyhwp)으로 변환한 사본(2건, 포함 대조라 줄 순서·중복은 보증하지 않음)으로 대조해 일치했다. 고유 .hwp 152개 중 151개가 열렸고(못 연 1개는 PDF를 이름만 .hwp로 바꾼 파일), 열린 151개는 HWPX로 내보낸 뒤 읽은 표와 같았다.
- 위험과 대응: PyPI `Development Status :: 3 - Alpha`인 신생 바인딩이다(성숙도는 위 「HWPX·HWP 추출」 표). 버전을 0.8.1로 고정하고, 엔진 호출은 `specton/ingest/hangul_engine.py` 한 곳에만 두며, 엔진을 불러올 수 있는 환경에서는 엔진 블록 클래스 이름·필드가 바뀌면 CI 시험이 실패하게 했다.
  - 리눅스 휠 문제: 0.8.1의 리눅스 휠은 묶어 둔 libfreetype에 `FT_Palette_Data_Get`가 없어 `import rhwp`가 실패한다(상류 DanMeon/rhwp-python #31, 미해결). 시스템 libfreetype을 `LD_PRELOAD`로 먼저 불러오면 import가 된다(Ubuntu 24.04 x86_64 컨테이너에서 확인). 엔진은 처음 읽을 때 불러와 실패해도 앱은 뜨고 한글 파일만 안내로 멈춘다. CI는 한글 시험을 시스템 libfreetype 선로드와 `SPECTON_REQUIRE_ENGINE=1`로 한 번 더 돌려 엔진 시험을 건너뛰지 않는다(`.github/workflows/ci.yml`). 실행 이미지(`Dockerfile`)도 시스템 libfreetype을 선로드하고, `--target check` 단계에서 `import rhwp`를 확인한다(#233). arm64에서는 빠진 함수가 `FT_Palette_Select`로 다르지만 같은 선로드로 import된다.
  - 0.5.1 이하 고정은 채택하지 않았다: import는 되지만 실제 hwpx에서 `<`·`>`·`&` 글자를 조용히 잃는다(실제 hwpx 3종 중 2종에서 확인).
- 구현 범위 밖: 서술형(표가 아닌 문단) 요구사항과 완전 서술형 비정형 문서, 상세표가 아닌 양식, 수정된 요구사항(취소선 등 변경 표시)은 읽지 않는다. 상세표와 서술형이 섞인 파일의 서술형 부분은 안내 없이 빠질 수 있다. 상세표가 하나도 없는 파일은 안내로 멈춘다. 암호 걸린 .hwpx는 읽지 못한 파일로 처리되어 일반 안내로 끝난다(암호 전용 안내는 업로드 단 팝업으로 따로 정했다).
- 시험함: 암호 걸린 .hwp 1개는 엔진이 거절해 파일 단위 안내로 멈춘다(2026-11-09, #201). 업로드는 `.hwpx`·`.hwp` 모두 받고, `.hwp`는 OLE 복합 문서 서명이 없으면 415다(#250).
- 아직 시험하지 않음: 배포용(편집 불가) 문서(#253), 구역이 2개 이상인 요구사항 RFP. HWP 5.0 이전 버전은 사용 현황을 조사한 뒤 지원 범위를 정한다(조사 전).
- PDF 추출·스캔 OCR은 위 결정대로 제안 상태이고, PDF 출력은 위 「PDF 출력」 결정대로 승인 상태다.

## 결과

- 좋아지는 점: 표가 많은 문서에 강하고 한글 PDF 출력 경로가 단순하다.
- 감수할 점: Docling 모델 다운로드·한글 폰트를 컨테이너 이미지에 포함해야 한다.
- 감수할 점 (PDF 출력): `mermaid-cli`는 Chromium을 포함해 이미지가 크다(실측 이미지 2.28GB, WeasyPrint 쪽 542MB). 배포 이미지(ADR-0013, #25) 크기에 반영한다. WeasyPrint는 Windows에서 GTK가 따로 필요해, PDF 시험은 Docker·CI(리눅스)에서 돌리고 Windows 로컬에서는 건너뛴다.
- 감수할 점 (Mermaid 11.17.2): 11.15.0의 mermaid 경보 5건(CSS 주입, 설정 API 프로토타입 오염, architecture 프로토타입 오염, XY 차트 무한 루프, radar DoS)은 11.16.1에서 고쳐졌다(#212). katex 낮음 1건(GHSA-238p, 0.18.2에서 수정)은 mermaid 11.x가 katex `^0.16`을 요구해 남고 mermaid 12.x(#211)로만 해소된다. 이 경보는 이미 있는 프로토타입 오염을 전제로 한다(#190 리뷰). 팀 결정(#13)대로 웹·PDF 같은 버전 고정을 유지하되, `securityLevel: 'strict'`와 「서버가 만든 원문」만으로는 막히지 않는다(#190 R1 실험: 별칭 따옴표 안의 `init` 지시문 `themeCSS`가 strict에서도 인식됨). 그래서 위 「Mermaid 설정 보안」을 웹과 PDF 모두에 적용한다. 올릴 때는 웹과 mermaid-cli를 함께 올리고 한글 ERD를 다시 실측한다.
