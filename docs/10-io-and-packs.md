# 문서 입출력·도메인 팩

> 상태: **초안** (엔진·양식은 회의 결정 전)

## 입력 처리 원칙

- 현재 입력은 Excel·CSV·HWPX·HWP다. 한글 입력은 요구사항 상세표를 읽는다. PDF 입력은 이번 인수 범위 밖이며, PDF 출력과 구분한다(#10, REQ-02).
- 모든 형식이 같은 단계를 거친다: **추출 → 스키마 구조화(원문 기호 보존) → 원문 대조 검증 → 사용자 확인**.
- ①·•·가. 같은 원문 기호와 번호는 정규화하면서 지우지 않는다.
- 원문 `source_ref`와 추출본을 보존하고, 추출본은 사용자가 고치지 않는다. 추출 확인 결정(확인·제외)과 사유는 원문 블록에 따로 남긴다 (ADR-0015). 추출 오류가 분석 품질 오류와 섞이지 않게 평가한다.
- 업로드 파일명을 저장 경로로 쓰지 않는다. 입력은 비신뢰 데이터다.

## Excel·CSV

| 항목 | 기준 |
|---|---|
| 기준 열 (제안, ADR-0003) | 요구사항 ID · 구분 · 요구사항명 · 상세 내용 · 출처 + 선택 "관련 요구사항" |
| 다른 양식 | 공공 7칸(ID·명칭·상세·분류·산출정보·관련 요구사항·출처), 스마트공장 11칸 등은 열 매핑 YAML로 기준 열에 맞춤 |
| 구분 열 | 원문값으로 보존. FR/NFR 정답으로 강제 해석하지 않음 |
| Excel | openpyxl로 값·시트/행 위치 보존. 수식은 실행하지 않음. 캐시값이 없거나 의미가 불명확하면 사용자 확인. 매크로 파일 불허. 병합 칸은 왼쪽 위 값으로 채우고, 요구사항 ID 칸이 세로 병합된 행들은 1건으로 묶는다 |
| CSV | Excel과 같은 열 매핑. 인코딩(UTF-8·CP949, BOM 있는 UTF-16)·구분자 확인, 행 번호를 `source_ref`로 |
| 지원 밖 | 병합 셀·다중 시트·헤더 위치 차이 중 지원하지 않는 것은 오류/확인 대상으로 안내 |

## PDF 입력 — 범위 밖(후속)

10/29 결정 2와 11/2 #10 공지에 따라 이번 인수 범위에서 제외하며, 2026-11-10 R1이 재확인했다. REQ-02·TC-F02는 필수 인수·평가 항목에 포함하지 않는다. API는 `.pdf`를 415로 거절한다. 다음 표와 엔진 후보는 향후 입력 지원을 다시 결정할 때 사용할 제안이며 현재 구현을 뜻하지 않는다. 아래 출력 규격의 PDF 생성은 계속 지원한다.

| 유형 | 처리 |
|---|---|
| 텍스트형 | 페이지·블록·읽기 순서 보존, 원문 대조 |
| 표형 | 셀/행 연결과 페이지 경계 확인 후 요구사항 블록으로 정규화 |
| 스캔 | OCR 포함 여부 미정 (ADR-0004). 미지원이면 명시 |
| 암호화·손상 | 오류와 지원 경계 안내, 추출 성공으로 처리하지 않음 |
| 도면 중심 | 도면에서 요구사항을 추론하는 기능은 범위 밖 |

- 엔진 제안: Docling(표 구조·OCR), 텍스트형이 느리면 pdfplumber 보조 (ADR-0004). 대표 PDF 2~3건으로 실측 후 확정.
- 추출 confidence를 항상 얻을 수 있다고 가정하지 않는다. 빈 블록·문자 깨짐·분리된 행으로 검토 플래그를 만든다.

## HWPX·HWP

| 유형 | 처리 |
|---|---|
| HWPX | 요구사항 상세표를 읽어 구역·문단·표·셀 위치를 `source_ref`로 (`specton/ingest/hangul.py`) |
| HWP 5.0 | 변환 없이 같은 파서로 읽는다. 위치는 HWPX와 같은 칸이고 `file_format`만 `hwp`(#24). 업로드는 OLE 복합 문서 서명만 먼저 확인한다(`specton/api/uploads.py`) |
| 배포용·암호화·손상 | 파일 단위 안내로 멈춘다(정상 분석으로 진행하지 않음). 암호 걸린 .hwp는 시험함, 배포용 문서는 시험 파일이 없어 미시험(#253) |

- 연결: 업로드(웹·API) → parse 노드(`specton/parse_node.py`의 형식별 파서) → 추출 확인. 한글도 xlsx·csv와 같은 `TabularResult`를 돌려주므로 이후 흐름은 같다(#24).
- 원문 기호(①·•·가. 등)와 줄바꿈은 고치지 않고 `source_text`에 그대로 둔다(앞뒤 공백만 뺌). 실제 엔진 시험: `tests/unit/test_hangul_input.py`.

- 엔진: HWP 5.0·HWPX 모두 `rhwp-python==0.8.1`(MIT)로 읽는다(2026-11-08 채택, ADR-0004). 엔진 호출은 `specton/ingest/hangul_engine.py` 한 곳이다.
- 원문 위치는 구역·문단·표·셀로 적고, 렌더링 쪽 번호를 원문 쪽 번호로 쓰지 않는다.
- 지원 여부를 화면에 명시한다.

## 도메인 팩

구조와 작업 방법은 [domain_packs/README](../domain_packs/README.md).

- `common`: 명명·타입·공통 규칙 (공공데이터 공통표준 8차, 2025-11 기준)
- 현재 완료·평가 범위는 `inventory`(재고·자재)와 공통 팩이다. `maintenance`(설비)는 후속이며 현재 완료 조건에서 제외한다.
- manifest에 이름·버전·출처·origin·승인 상태를 기록한다.
- 팩 값의 근거와 출처는 [common 근거](../domain_packs/common/RATIONALE.md), [maintenance 근거](../domain_packs/maintenance/RATIONALE.md)에 둔다.
- 미지원 도메인의 자동 외부 검색은 후속 확장(EXT-01)이다.
- 개발용 합성 요구사항(재고 INV-xxx, 설비 MNT-xxx)은 팩 보완·few-shot에만 쓴다. 세트 전체는 공개 저장소에 올리지 않고, few-shot에 넣는 범위는 [07 테스트·평가](07-testing-eval.md#평가-데이터)를 따른다. 정답 ERD·DDL을 평가 입력에 함께 넣지 않는다.
- 팩의 `patterns.yaml`에 있는 `development set assumption Axx`는 개발용 세트 문서의 가정 번호다. 에이전트 ID(A01~A09)와 다르다.

### 팩 형식 결정 사항 (ADR-0009)

| 항목 | 확정 기준 |
|---|---|
| 타입 프로필 | `strict` (일자 char(8), 여부 char(1) Y/N) / 대안 `pg_native` |
| 조합 코드 길이 | 업무 코드 `코드C10`, 유형·상태 코드 `코드C2` (개발 요구사항 기준) |
| 공유 용어·패턴 | 도메인 용어·패턴은 각 팩에 유지. 공통 단어·도메인·명명·규칙만 공유 (ADR-0009) |
| 명명 규칙 | 접두어 없음, PK 용어 물리명·FK 부모 키, 단어 수 제한 없음 (ADR-0009) |
| 공통표준 판 | 8차 CSV·sha256 고정. 9차 자동 도입 없음 |
| 팩 파일 형식 | Pydantic 모델로 고정 (로더·검증 테스트) |

## 출력 규격

| 산출물 | 형식 | 필수 내용 |
|---|---|---|
| 요구사항 분석 | Markdown (중간) | source_id·REQ-xx·원문 위치·분류·질문 |
| 기능 명세서 | Markdown + 최종 PDF | 기능 ID·설명·우선순위/근거·req_ids·CRUD |
| ERD | Mermaid + 최종 PDF | 엔티티·속성·키·관계·선택 여부, 모델 버전 |
| DDL | SQL | PostgreSQL 대상·모델 버전·검증 상태 |
| RTM | Excel·CSV | 원문 요구 → 기능 → 엔티티/관계, 연결·미연결 표시. 추출 확인에서 뺀 원문은 「제외」 행과 사유(없으면 판정 이유), 원문 문장 없이 확인한 행은 「확인(원문 없음)」 행과 판정 이유로 남기며 둘 다 미연결로 세지 않는다 (ADR-0015) |
| 검토 결과·승인 기록 | 최종 HITL 확인·승인, revision별 DB 저장·화면 조회 | 심각도·대상·근거·수정 제안·검토 출처·SQL 검증 상태. 승인 후 같은 revision의 지적 재조회. 별도 Markdown 보고서·전용 보고서 화면은 만들지 않음(2026-11-10 R1 확정) |

- PDF는 생성 단계에서 최종 Markdown·Mermaid를 변환한 비공개 후보로 저장한다. 승인 때 같은 파일 해시를 근거로 고정하며 승인 후 재렌더링 없이 동일 바이트를 공개한다.
- 기능 명세서 Markdown(`specton/codegen/function_spec.py`, #14)은 문서 정보(`run_id`·`revision`·`model_hash`·`pack`·`pack_version`, ERD PDF 표지와 같은 이름) → 기능 목록 → 기능 상세 → CRUD 매트릭스(면제 근거 포함) 순서다. 제목·문단·글머리표·굵게·인라인 코드·파이프 표만 쓰고(글 안의 `\`·`*`·`` ` ``는 역슬래시로, 표 칸의 `|`는 그 뒤에 이스케이프), 초안 표시는 넣지 않는다(승인본이 같은 바이트라 초안 구분은 파일 이름·PDF가 한다).
- PDF 엔진: WeasyPrint(HTML/CSS → PDF) + `mermaid-cli`(SVG), Mermaid 11.17.2 (웹과 같음, #223). 기능 명세서와 ERD가 같은 엔진을 쓴다. ERD가 깨지면 Playwright 인쇄로 전환 (ADR-0004 승인).
- 한글 폰트(Noto Sans CJK KR)·긴 표 페이지 분할·머리글 반복·ERD 배율은 실측으로 확인했다. ERD는 개요 + 영역별 상세도(키 속성만) + 테이블 정의서로 나누고, 넓은 표는 가로 쪽에 두되 넘치면 열을 나눈다 (ADR-0004 「PDF 출력 실측」).
- 렌더러가 외부 경로·URL 리소스를 가져오지 못하게 제한한다.

### 검토 결과·승인 기록

- 검토 지적은 `Finding`으로 스냅샷에 저장하고 `GET /runs/{id}/view?section=review&revision=…`로 조회한다. 최종 HITL은 지적·설계·SQL 검증 요약을 표시하고 승인·수정 요청·보류를 받는다. critical 차단과 SQL 검증의 필수 정책은 서버가 다시 검사한다. 검증 기록과 사람 승인은 같은 뜻이 아니다.
- 승인 이후에도 결과 작업공간의 「검토」 탭에서 revision별 내용을 조회한다. 승인 결정·산출물 근거는 기존 approval·approval_basis로 보존하며, 새로운 보고서 파일을 만들어 승인 근거를 대체하지 않는다.
- `review/md`는 API·저장 호환 목록에 남기되 현재 생성 대상에는 포함하지 않는다. 다운로드 화면은 실제 파일이 없는 검토 보고서 행을 만들지 않는다. 과거 실행에 실제 검토 파일이 있으면 기존 다운로드를 유지한다.

### 출력 manifest

`run_id`, `revision`, `model_hash`, `source_hash`, 팩·프롬프트·생성기 버전, 승인 상태, 파일별 해시. 초안과 승인본의 내용 버전을 섞지 않는다.

- 구현: `specton/codegen/manifest.py` `build_manifest`·`render_manifest`(키 순서를 고정한 JSON, #14). 한 manifest에는 현재 revision·현재 모델·같은 승인 상태의 파일만 넣고, 섞이면 만들지 않는다. 자신의 해시는 파일 목록에서 제외한다. 생성기 버전은 모델 정리 규칙 버전·이름 규칙 해시다. #17의 `manifest_node`가 최종 검토 직전 `manifest/json` 비공개 후보를 저장하고, 승인 근거에 고정한 같은 바이트를 승인 후 내려받는다. JSON의 `approved=true`는 최종본 내용이고 실제 승인 여부는 산출물 메타데이터·DB 승인 기록을 따른다.
- RTM(`specton/codegen/rtm.py`, #14): 시트 「RTM」(원문 ID·원문 위치·요구사항 ID·상위 요구사항·요구사항·유형·기능·엔티티·관계·상태·비고)과 「문서 정보」(기능 명세서와 같은 문서 정보 + 상태별 건수). CSV는 같은 행을 UTF-8(BOM)·CRLF로 쓴다. 상태는 `연결`(기능에 하나라도 연결)·`미연결`·`제외`·`확인(원문 없음)`이고, 연결은 `req_ids` ID 조인만 쓴다. 같은 입력이면 같은 바이트다(xlsx 작성 시각 고정). 글 칸은 수식이 아닌 문자열로 쓰고(CSV는 `=`·`+`·`-`·`@`·탭·CR로 시작하면 앞에 `'`), 엑셀 한 칸 한도(32,767자)를 넘는 글은 「긴 글」 시트에 조각으로 모두 남긴다.
- **RTM 보류 기준 확정 (2026-11-10 R1, #17 인수 잔여):** REQ-12의 행 상태는 `연결`·`미연결`·`제외`·`확인(원문 없음)` 네 가지다. HITL 2의 `hold`는 실행을 같은 확인 요청에서 기다리게 하는 결정이며 RTM 행의 별도 상태가 아니다. 보류·재시작은 RTM 파일을 다시 만들거나 행을 보류로 바꾸지 않는다. NFR도 기능과 이어지지 않으면 `미연결`이며, 비기능이라는 이유로 보류·제외 처리하지 않는다. 보류 실행 이벤트와 최종 승인 결정은 기존 실행/승인 기록을 따르며 원문 제외 사유와 혼합하지 않는다. 행별 보류 사유가 필요해지면 새 계약·기준을 별도 변경 요청으로 정한다.

### #11 고정·처리 정책 (2026-11-09)

재고·공통 팩의 고정 기준은 ADR-0009를 따른다. common 0.1.5와 inventory 0.1.21은 approved이며
`pack.lock`과 `sources.yaml`로 내용을 고정한다. `handling`과 `target_stage`의 의미는 ADR-0009 표를 따른다.
SC에 critical을 설정하거나 참고 의견을 major로 설정하면 로더가 거절한다.
`standard_selection.yaml`의 예외는 로더와 `python -m specton.packs.build --check`가 검증한다.
정리 결과의 `common_version`·`policy_digest`는 모델 스냅샷과 manifest에 보존한다.
정리 후 팩·표준 원본이 바뀌면 규칙 노드는 다른 정책으로 이어 가지 않고 실행 오류로 중단한다.
평가 문서·정답은 이 고정 작업의 입력으로 사용하지 않는다.


### 정리 명명 사전·중복 참조 지원 (common 0.1.6)

공통 단어 생성은 고정 공식 CSV의 폐기 제외 전체를 사용한다. 팩의 용어 수에 맞춰 단어를 줄이지 않는다. 명명 우선순위는 공통 단어 → 팩 단어 → 팩 용어이며, 전체 사전에도 없는 이름은 RULE-05 사람 조치로 유지한다.

`column.repeated_foreign_key`는 `manual`(기존 정책) 또는 `relationship_id`다. 후자는 같은 부모·자식의 반복 1:1/1:N 참조를 관계 ID 해시 접미어로 모두 구분한다. 역할을 자유 문장에서 추론하지 않고 원래 관계와 근거를 그대로 보존한다. 길이·충돌·DDL 검사도 유지한다. 변경된 정리 결과는 normalize-v1·새 common 버전으로 기록하고 기존 승인 run에는 적용하지 않는다.

미지원 이름은 RULE-05·critical·사람 조치로 유지한다. 의미가 같은 등록 표현인지 사람이 확인하고,
신규 등록은 출처·약어 검토 후 새 버전에서 한다. 평가 관측에 맞춘 등록·프롬프트 수정은 고정 평가와
분리한다. D13은 기존 속성이 중복 FK인지 독립 업무 값·키인지 확인해 설계를 고치며 일괄 삭제하지
않는다. D4는 다른 부모의 키끼리도 생기므로 관계·키를 합치지 않고 명명 지원을 확인한다.
A03·A04는 재작업 때 직전 설계와 지적을 `rework_context`로 받는다. 최초 실행·few-shot에는 이
필드가 없고, 결과 계약·사람 조치 우선·critical 승인 차단은 유지한다.
