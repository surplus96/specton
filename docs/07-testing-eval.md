# 테스트·평가

> 상태: **초안** (평가 목표값은 회의 결정 전)

## 테스트 층위

| 층위 | 대상 | 환경 | 명령 |
|---|---|---|---|
| 단위 | 파서·ID·규칙·템플릿·노드 계약·병합 | pytest, 고정 LLM 응답, DB/API 호출 없음 | `uv run pytest` |
| DB 통합 | SQL 문법·허용 문장·FK·트랜잭션 | pglast + PostgreSQL 18 sandbox | `uv run pytest -m db` |
| API·그래프 통합 | 업로드·상태·SSE·HITL·병렬 합류 | 테스트 client + 영속 상태, LLM stub | `uv run pytest tests/integration` |
| 실제 LLM 평가 | 분류·기능·모델·검토 | 승인 데이터, 모델·팩·프롬프트 고정 | `uv run pytest -m llm` (수동, 이번 시범·평가 총 약 $100·실행 한도 적용, ADR-0007) |
| 사용자 수용 | 입력 → 수정 → 승인 → 출력 | React 웹, 개발/AWS 환경 | `tests/e2e/` (도구 미정) |

- `pyproject.toml`에서 db·llm 마커를 등록했고 기본 실행에서 제외한다.
- CI는 API 키 없이 ruff·mypy·단위 테스트·팩 검사를 실행한다 (`.github/workflows/ci.yml`). DB 통합 작업은 격리 서비스를 준비한 뒤 추가한다.
- stub 테스트 통과를 실제 모델 품질 통과로 표시하지 않는다.
- 테스트는 구현을 다시 서술하기보다 오류·경계·실패 복구를 확인한다.

## 테스트 케이스

TC 37개(기능 `TC-F01`~`F22`, 비기능 `TC-N01`~`N06`, 에이전트 `TC-A01`~`A09`)의 시나리오·기대 결과는 [12 테스트 케이스](12-test-cases.md)에 있다. 요구사항 대응은 [02 요구사항](02-requirements.md). TC마다 실행 상태는 12 문서의 마지막 칸에 적는다. stub 단위 통과와 실제 모델 실행(#49)은 구분해 적는다.

## 평가 데이터

| 세트 | 용도 | 규칙 |
|---|---|---|
| 개발용 | 도메인 팩 보완·few-shot·디버깅 | 재고 INV-001~016, 설비 MNT-001~022 합성 요구사항(처음 세트). R2 합성 세트(2026-11-08): 개발용 17건, 퓨샷용 12건 |
| 평가용 | 성능 측정 | 팩 작성자가 보지 않은 별도 문서. 팩을 이 세트에 맞춰 고치지 않음 |

- 개발용 세트를 새 합성 세트로 바꿔도 처음 세트(INV-001~016, MNT-001~022)는 지우지 않고 남긴다. 고정한 재고 팩의 출처(`manifest.yaml`, `patterns.yaml`, `examples/*.yaml` 주석)와 설비 팩 `RATIONALE.md`가 그 ID를 가리킨다.
- R2 합성 세트의 시연용 17건은 현장 시연 전용이다. 개발·few-shot·평가에 쓰지 않는다.
- 평가 세트: 재고 5건. 설비 3건은 구현 완성 전까지 제외하고, 시간이 남으면 추가한다 (ADR-0014, #40).
- 평가 세트 수집·정답 작성은 R3 박성진이 맡는다. 팩 작성자(R2)와 다른 사람이어야 하며, R2는 팩을 고정한 뒤에만 평가 문서를 본다 (ADR-0014).
- 각 자료는 원문·출처/라이선스·`origin`·승인 상태·정답(분류·기능·모델)·허용 대안·심은 결함·문서 해시를 갖는다. 합성 자료는 `origin: synthetic`.
- 같은 원본의 변형을 독립 문서처럼 나누지 않는다. 원본 계열 단위로 분리한다.
- 정답은 구현 결과를 보기 전에 검토하고, 변경 사유·버전을 기록한다. 모델 출력에 맞춰 정답을 고치지 않는다.
- 평가 전 팩 버전을 `status: approved`로 고정한다.
- 개발용·평가용 데이터와 정답은 **공개 저장소에 올리지 않는다.** 팀 비공개 구글 드라이브에 두고(링크는 저장소에 적지 않는다), 저장소에는 데이터 없이 실행되는 코드와 집계 결과만 남긴다 (ADR-0014).
- few-shot 예시(`domain_packs/*/examples/`)는 개발용 세트에서만 만든다.
  - `input`에는 개발용 세트의 요구사항 문장을 그대로 쓸 수 있다. 개발용 세트는 공개 기능 문서를 참고해 팀이 새로 쓴 합성 자료라 라이선스 제약이 없다 (PR #66 리뷰).
  - 예시마다 그 예시에 필요한 요구사항 몇 건만 넣고 `source_id`에 원문 ID를 적는다.
  - `output`은 담당자가 노드 출력 모델에 맞춰 직접 쓴다. 참고용 기대 결과를 그대로 옮기지 않는다.
  - 넣지 않는 것: 개발용 세트 전체, 참고용 기대 결과(기능 명세서·ERD·DDL·RTM) 원본, 외부 제품의 문서 문장·코드·DB 덤프, 평가용 세트 문서.

### 재고 평가 자료 승인·인계 완료 (2026-11-10, #40)

R1은 R3의 전체 승인 완료를 확인하고 #40의 자료 준비·승인 범위를 완료로 판정했다. 승인 범위는 재고 평가 5건, A01 정답 v0.3·기능/모델 정답 v0.2와 허용 대안, 문서별 `origin`·출처/라이선스·해시 기록, A05/A08 고정 설계·심은 결함·기대 탐지 결과와 관련 승인 기록이다. 자료와 상세 승인 장부는 팀 비공개 위치에서 관리하고 #20 평가에 인계한다.

이번 완료 기록의 근거는 R1이 확인한 R3 전체 승인이다. 비공개 파일이나 해시를 이번 문서 변경에서 다시 검증한 것으로 적지 않는다. R1의 기존 정답 수정·승인 겸임 및 최초 평가의 독립성 제한은 당시 기록과 함께 보존한다.

실제 실행·의미 대응·채점과 팩 비교는 #20, 리뷰 방식 비교는 #18에서 계속 추적한다. TC-N04의 전체 시나리오 통과 여부는 실제 실행 근거에 따라 별도로 기록한다.

## 지표

운영 사전 출처 검증(#291)은 평가 전용 A08 확장 사전과 별개다. inventory 0.1.23은 이미 #299에서
승인한 개발용 어휘의 출처를 기계 검증하며 평가 원문·정답·관측 이름을 선정 입력으로 읽지 않는다.
처음 고정한 common 0.1.5·inventory 0.1.21의 결과는 보존하고 새 팩의 재실행은 관측 후 회귀·진단
조건으로 따로 보고한다. 기존 정답·점수·승인 해시를 바꾸지 않는다. #291의 출처 검증은 의미·선정
검토·실제 평가 실행을 대신하지 않는다. 이번 변경은 R1 최종 검토 완료로 기록하며(ADR-0009),
평가 전용 사전 합성 기능은 추가하지 않는다.

| 영역 | 지표 |
|---|---|
| 분류 | FR/NFR별 precision·recall·F1, macro F1, 혼동행렬 (정확도만 보고하지 않음) |
| 기능·엔티티·관계 | 승인 기준과 일대일 또는 허용 분할/병합 매칭 후 TP/FP/FN. micro/macro 단위 명시 |
| 결함 탐지 | 심은 결함 대비 발견율, 보고 지적 중 실제 결함 비율, 정상 사례 오탐 수. rule/llm/필터 이후 구분 |
| DDL | 실행 성공 문서 수 / 평가 대상 전체. 미생성·파싱 실패·실행 실패 별도 집계 |
| 비용·시간 | run별 모델·입출력 토큰·재요청·재작업·벽시계 시간. 단가 적용 시 기준 날짜 기록 |
| 문서 추출 | 형식별 추출 누락·잘못 합침·원문 기호/위치 보존 (설계 성능과 분리) |
| 팩 효과 | 같은 입력을 팩 적용/미적용으로 실행해 F1 비교 (다른 버전은 고정) |
| 리뷰어 방식 | `parallel` vs `combined`의 탐지율·오탐·토큰·시간 (ADR-0008) |

- F1 = 2PR/(P+R). 분모가 0일 때의 집계 정책을 미리 정하고 사례 수를 함께 보고한다.
- 목표값은 첫 기준 실행 후 정한다 (ADR-0014). DDL 실행 성공 100%는 승인된 평가 집합에만 적용한다.

## 검토 관점 평가

검토 관점(A05~A08)의 결함 탐지는 생성 결과가 아니라 **고정 설계**로 잰다. 원문만 고쳐서는 설계 단계가 원문대로 맞게 만들면 결함이 심어지지 않기 때문이다 (#40, A05 결정).

- 고정 설계 파일: 관점 하나에 YAML 하나. 사례마다 원문 ID와 그 문장에 대한 설계 한 벌을 둔다. 형식은 합성 예시 `tests/unit/data/review_eval_sample.yaml`.
  - `reviewer_id`(관점), `set`(평가 세트 이름·버전), `pack`(few-shot 예시를 넣을 팩), `cases`
  - 사례: `case_id`, `source_id`(근거 원문), `case`(`normal` 정상 · `alt_normal` 같은 요구를 다르게 표현한 정상 · `defect` 결함), `requirements`(`id`·`text`·`type`·`nfr_category`), `functions`(선택), `entities`(`id`·`name`, 선택 `description`·`req_ids`·`attributes`), `relationships`(관점 예시와 같은 칸), `expected`
  - `expected`: `defect` 사례에만 `{target: 설계 요소 ID, defect: cardinality | direction | optional | identifying}`. 결함은 사례마다 하나씩 심는다.
  - 파일에 없는 계약 필수 칸(원문 위치·설명·키 속성·관계 근거)은 도구가 중립 값으로 채운다. `description`·`rationale`은 파일에 쓰면 그대로 쓴다.
- 채점: 지적 대상(`targets`)의 종류·ID가 기대 대상과 같으면 맞춘 것이다. 지적 `kind`는 LLM이 정하는 글자라 채점하지 않고 보고서에만 남긴다.
  - 발견율 = 맞춘 기대 결함 / 기대 결함, 지적 정확도 = 기대 대상을 가리킨 지적 / 전체 지적, 정상 오탐 = `normal`·`alt_normal` 사례의 지적 수
  - 호출이 실패한 사례는 지적 0건으로 세지 않고 실패로 따로 센다. 지표 계산에서는 뺀다.
- 실행: `uv run python -m specton.review.eval_fixtures <고정설계.yaml> --out <결과.json>` (`specton/review/eval_fixtures.py`). 사례마다 `review_perspective`로 그 관점만 실제 LLM으로 돌린다(`SPECTON_OPENAI_API_KEY` 필요). 결과 파일에는 사례별 지적·찾은/놓친 대상·지표·프롬프트 버전·모델·토큰이 들어간다.
- 고정 설계 파일과 결과 파일은 평가 자료다. 공개 저장소에 두지 않는다 (위 「평가 데이터」).
- **A08:** 모든 엔티티의 `attributes`를 명시한다. 각 속성은 저장 계약의 `id`·`name`·`data_type`·`req_ids`와 타입 크기·키 여부·NULL 허용 등을 사용한다. A05의 생략된 키 보충을 A08에 적용하지 않는다. `normalized`를 파일에 직접 쓰지 않는다.
  - `Settings.pack_root`에서 승인된 도메인·공통 팩을 읽고 실제 내용이 `pack.lock`과 같은지 검사한 뒤, 버전을 상태에 기록하고 `normalize_design`으로 정리한다. 모든 사례를 LLM 호출 전에 준비한다. 한 사례라도 정리에 실패하면 사례 ID·문제 코드로 평가 자료 오류를 내며 미탐·정상으로 세지 않는다.
  - A08의 `expected.target`은 원래 엔티티·속성·관계 ID다. `defect`는 `multi_value`·`repeating_group`·`duplicate_fact`·`transitive_dependency`·`partial_dependency`·`derived_value` 중 하나이며 채점은 A05와 같이 대상 ID 기준이다. 정리 테이블·컬럼 ID를 기대 대상으로 쓰지 않는다.
  - 결과에 사례별 팩·공통 버전, 정책·사전 해시, 정리 규칙 버전과 모델 해시를 남긴다. 파일 전체의 파싱된 내용 해시(`fixture_content_hash`)와 사례별 호출 기록(모델·토큰·재요청·호출 소요시간)도 기록한다. 호출 소요시간 합계는 전체 벽시계 시간과 구분한다. 사례 전체에서 실행 토큰 예산을 공유하며 소진 뒤 후속 호출은 `BUDGET_EXCEEDED` 실패로 남긴다. 합성 형식 예시는 `tests/unit/test_eval_a08.py`다.
  - **본 평가 사전 범위:** 고정된 승인 재고·공통 팩 그대로 정리에 성공하는 사례로 측정한다. `multi_value`·`repeating_group`도 같은 진입 조건을 적용한다. 정리에 막히면 평가 자료 오류이며 미탐으로 세지 않는다. 해당 유형을 측정하지 못했으면 유형별 사례 수 0·미측정과 사유를 명시한다. 다른 네 유형의 결과로 여섯 유형 전체를 검증했다고 쓰지 않는다.
  - **별도 탐색 조건:** 사전 보완이 필요한 사례는 본 평가와 합산하지 않는다. 평가용 사전은 별도 사본·버전·해시·추가 어휘와 선정 근거를 기록하고 R1·R4가 실행 전에 검토한다. 평가 정답으로 운영 팩·few-shot을 보완하지 않는다. [탐색 사전 합성 도구](20-evaluation-lexicon.md)는 기준 팩과 출처의 별도 사본을 만들고, 선정 해시에 연결된 두 역할의 승인 기록을 확인한 뒤 명시적인 A08 탐색 조건으로만 실행한다. 사본 생성이나 도구 구현을 실제 자료 승인·실행 완료로 세지 않는다. 고정 팩을 수정하거나 조용히 기본 팩으로 우회하지 않는다.

### A05 고정 설계 작성·인계 (#40)

실행 전 `python -m specton.review.fixture_audit <고정설계.yaml> --out <새 감사.json>`으로
입력 SHA-256·정상 구조 묶음·기대 대상 단위·생략 속성·출처 ID의 유형명 단서를 확인할 수 있다.
이 명령은 API·DB를 호출하지 않고 기존 출력 파일의 덮어쓰기를 거절한다. 결과에는 비공개
사례 ID와 정답 대상이 포함되므로 평가 자료와 함께 비공개로 보관한다.
구조 해시는 ID·이름·속성·관계를 포함하고 설명·근거는 제외한다. 같은 해시도 의미 동등성을
증명하지 않고, 다른 ID로 표현한 같은 구조를 찾아내는 그래프 동형성 검사도 아니다.
유형명 일치는 검토 단서이며 실제 모델 입력 노출 여부는 별도로 확인한다.
이 점검은 정리 성공·정답 승인·자료 독립성을 대신하지 않는다.

## 오프라인 통합 채점 (#20)

실제 실행과 채점을 분리한다. `python -m specton.evaluation input.json --out report.json`은 승인된 정답·매칭과 저장된 실행 결과를 읽으며 LLM·DB에 접속하지 않는다. 입력과 결과는 평가 자료이므로 팀 비공개 위치에 둔다. 기존 파일은 덮어쓰지 않는다.

- 입력 형식은 `specton/evaluation/models.py`의 `Evaluation`이다. `dataset`, `gold_version`, `gold_variant`, `gold_hash`, `approval_ref`, `gold_status: approved`, `matching_status: approved`, `planned_document_ids`, `documents`를 받는다. 정답·매칭 승인을 이 도구가 대신하지 않는다.
- 문서마다 입력 해시·run ID·조건(`condition`)·반복 번호·완료/실패/취소/미완료/미실행 상태·코드/팩/공통/정책/모델/프롬프트 버전을 기록한다. 조건·반복마다 예정 문서를 모두 넣으며 미실행도 행으로 남긴다. 같은 조건의 버전 불일치, 같은 문서의 입력 해시 불일치는 거절한다.
- A01: 원문 ID·요구사항 ID·FR/NFR·필수/허용 경고를 승인 정답에서 변환한다. `alignments`는 같은 원문 안의 정답·출력 ID 일대일 대응이다. ID 문자열·문장 유사도로 추정하지 않는다. 원래 정답의 허용 분할안은 승인된 `gold_variant`로 명시하고 그 기준으로 대응을 준비한다.
  - FR/NFR precision·recall·F1, 라벨 macro F1, 문서 macro F1과 혼동행렬을 낸다. 대응이 없는 정답·출력도 각각 FN·FP에 포함한다.
  - 분할 수는 원문별 정답·출력 건수를 비교한다. `allowed_split_counts`가 있으면 사전 승인된 건수 중 하나면 분할 수 정답으로 세고 대표·허용·실제 건수를 함께 기록한다. 개수가 맞아도 내용이 틀린 분할은 의미 대응에서 인정하지 않는다.
  - 경고는 기본적으로 요구사항·종류 단위다. 원문 행 단위로 작성한 정답은 `source_warnings`에 배치하고 같은 원문 자식들의 경고 합집합으로 한 번만 센다. 해당 원문의 자식 `Truth`에는 경고를 중복 배치하지 못한다. `required_warning_groups: [[missing_value, ambiguous]]`는 둘 중 하나 이상이면 TP 1건, 둘 다 없으면 FN 1건이다. 필수·대안·허용 경고가 겹치면 거절한다. 허용 경고는 TP·FP에 넣지 않고 별도 집계한다.
- 기능·엔티티·속성·관계는 `objects`에서 승인된 동등 그룹을 받는다. 분할·병합을 허용한 그룹 하나를 TP 하나로 세고 남은 출력·정답은 FP·FN이다. 같은 대상을 여러 그룹에 재사용하거나 없는 대상을 매칭하면 거절한다. micro와 문서 macro, 측정 문서 수를 함께 낸다.
  - 선택 객체는 각 항목의 `permitted`에 별도 정답·출력·승인 대응을 둔다. 없으면 FN으로 세지 않고, 승인 대응이 있으면 해당 출력은 TP·FP에서 제외하며 `permitted_predictions`로 보고한다. 선택 엔티티의 속성·업무 키도 선택 대상이며 부모가 선택인데 자식만 필수 분모에 넣지 않는다. 필수와 선택 사이에서 같은 출력·정답 ID를 재사용할 수 없다.
- 결함 탐지는 `detections`의 `rule`·`llm`·`filtered`를 각각 받는다. 기대 결함 ID·지적 ID의 승인 매칭과 정상 사례 오탐을 센다. 입력하지 않은 항목은 측정 문서 수 0·점수 null이며 통과로 표시하지 않는다.
  - **허용 지적:** 각 채널의 `permitted`에 허용 결함 `gold`, 실제 지적 `predicted`, 승인된 `matches`를 둔다. 허용 결함은 탐지율 분모에서 빼고, 대응한 실제 지적도 TP·FP에서 제외한다. 미탐 FN을 만들지 않는다. 허용 대응 없이 지적 ID만 제외하거나 필수·허용 대상을 중복 사용하면 거절한다. 제외한 실제 지적 수는 `permitted_predictions`로 보고하며 정상 사례 오탐에도 적용한다. 예: `permitted: {gold: [optional-1], predicted: [finding-2], matches: [{gold: [optional-1], predicted: [finding-2]}]}`.
  - 허용 여부는 사전 승인 정답에 근거해 대상·내용으로 대응한다. `kind` 문자열이나 A06/A07 관점 이름만으로 지적을 자동 제외하지 않는다. A07(A06도 인정) 결함은 어느 쪽에서 탐지했든 같은 필수 결함에 승인 대응하며 중복 TP를 만들지 않는다.
  - 이 표현을 포함한 채점 정책은 `offline-v2`로 보고한다. 이전 `offline-v1` 보고서를 새 정책으로 실행한 것처럼 바꾸지 않는다.
- 품질 지표는 완료 실행을 대상으로 하고 제외한 실패·미실행 run ID와 상태를 보고한다. DDL 성공률 분모는 실패·미실행을 포함한 전체 예정 실행이며 미생성·실패·오류·미검증을 분리한다.
- 0분모 점수는 null이다. macro는 정의된 점수만 평균한다. 시간·입출력 토큰·재요청·재작업·비용은 실패 실행도 포함해 측정 건수와 합계를 기록하고, 미측정 값은 0으로 채우지 않는다. 비용을 입력하면 단가 기준 날짜·출처(`cost_basis`)를 함께 적는다.
- `specton.evaluation.observations`는 저장된 `DesignState`에서 A01 출력·품질 경고와 기능·모델 ID를 꺼낸다. A01 채점에는 사용자 수정 전 체크포인트를 사용하고, 원문 ID 변환은 명시적으로 제공한다. 원문·의미 매칭·정답을 생성하지 않는다.
- 합성 입력·숫자 예시는 `tests/unit/test_evaluation_scoring.py`다. R3 Excel 정답은 v0.3 승인 후 이 형식으로 변환하며 원본과 승인 해시를 보존한다. 원본 Excel을 직접 읽거나 평가를 실행하는 도구는 아니다.
- **정답 선택 준비:** `python -m specton.evaluation.preparation <비공개 준비목록.json> --out <선택계획.json>`은 준비 목록이 기록한 입력·정답 파일 해시를 재확인하고 원문별 허용 분할 수·승인 원문 셀·검토 항목을 보존한다. 원본 Excel을 재해석하거나 문장형 허용 대안을 추측하지 않는다. 혼합 분류·조건부 대안은 사람이 분할별로 정하고, 원문 단위 필수·허용 경고를 모든 자식에 복제하지 않는다.
  - 각 행의 `selection`에 `variant`, 선택 검토의 `approval_ref`, 분할별 `items`(`Truth`), NFR 항목별 `nfr_categories`를 채운다. 원문 단위 경고는 선택의 `source_warnings`에 넣는다. 원래 승인 정답 안의 대안인지와 경고 배치의 의미는 사람이 검토한다. 출력 관측 전에 대표안·허용 대안과 적용 조건을 고정한다. 관측 후에는 그 조건에 맞는 대안과 대응을 승인·기록하며, 점수가 높은 대안을 몰래 선택하지 않는다. 허용 분할 수만으로 조건부 대안의 분할 내용·분류까지 승인된 것으로 추정하지 않는다.
  - 같은 명령에 `--selections <검토완료 선택계획.json>`을 더하면 정답 측 입력만 변환한다. 해시·원본 행·대안 변경, 미선택, 분할 수 범위 위반, 다른 원문 참조, ID 중복, NFR 세부 분류 누락을 거절한다. NFR 세부 분류는 선택 기록에 보존하지만 현재 통합 지표는 FR/NFR만 측정한다.
  - 두 출력 모두 `ready_to_score: false`인 준비 자료다. 실제 채점에는 사용자 수정 전 A01 체크포인트, 명시적 원문 ID 변환·승인된 대응, 실행 버전·예산·결과가 별도로 필요하다. LLM·DB를 호출하지 않고 기존 파일을 덮어쓰지 않는다. 준비·선택 파일도 비공개 보관한다.
  - A01 정답 승인과 기능·모델 정답 승인을 구분한다. 모델 정답 v0.2는 2026-11-10 사용자 지시로 R1이 재검토·확정했고, 이후 R1이 R3의 전체 승인 완료를 확인했다(위 「재고 평가 자료 승인·인계 완료」). R1 수정·승인 겸임과 최초 평가의 독립 검토 제한은 당시의 비공개 승인 기록에 남긴다. 원본 Excel 해시는 보존하고 승인 상태·결정 근거는 별도 기록으로 연결한다. 허용 지적 표현·집계나 정답 승인은 의미 대응 승인·실행 예산을 대신하지 않는다.
- 조건별 보고를 제공하지만 팩 미적용·parallel/combined의 실제 실행을 만들지 않는다. 비교에서 바꿀 요소와 고정할 버전은 실행 전에 정한다 (#20·#18).

## 리뷰 실행 방식 실측 (#18, 2026-11-11)

기준 main `d62f16b`에 계측 도구를 추가해 새 합성 고정 설계 3종(정상, 관계 수 모순, 중복 사실)을 각 2회 실행했다. 두 번째 반복은 순서를 뒤집었다. 두 조건에 같은 설계·승인 팩(common 0.1.7/inventory 0.1.23)·모델(gpt-6-luna, low)·관점 프롬프트·스키마·동시성 4를 사용했다. 각 설계의 모델 해시와 입력 파일 해시, 호출별 프롬프트·토큰·가지 시작/종료와 실제 경과 시간은 [실측 기록](evidence/18-review-comparison-20261111.json)에 있다. 정답은 호출 입력에 넣지 않았다.

`run_comparison_condition`은 운영의 `review_nodes`와 GraphState reducer를 LangGraph의 4개 가지·합류에 연결한다. parallel을 순차 반복으로 대신하지 않는다. 정상/실패 가지 합류에는 실제 `merge_review`의 대상·인용 검사를 적용한다. 출력의 내용은 고정 기대와 대상·근거·수정 제안을 읽고 의미 대응을 검토했으며 kind 문자열로 맞추지 않았다.

| 방식 | 완료 | 기대 결함 TP/FN | 명백한 오탐 | 다른 관점의 중복 지적 | 입력/출력 토큰 | 평균 전체 시간(s) |
|---|---|---|---|---|---|---|
| parallel | 6/6 | 3/1 | 3 | 1 | 110,674/1,863 | 2.817 |
| combined | 6/6 | 4/0 | 0 | 0 | 67,634/1,866 | 4.746 |

관점별 기대를 기준으로 parallel 탐지 3/4, combined 4/4다. parallel에서 A06은 관계가 입력에 없어서 이미 존재하는 창고 연결을 세 번 누락으로 지적했다. A05가 A08 중복 사실을 한 번 추가 지적한 것은 내용상 거짓인 오탐과 구분했다. 관점별 지적 제한을 엄격히 채점하면 이 추가 지적도 기대 밖 1건이다. 이 입력 비대칭은 후속 결함 조치 대상으로 넘기고, 실측 중 프롬프트·팩을 바꾸지 않았다.

combined 기본값을 유지한다. 이번 작은 합성 진단에서는 combined가 토큰과 오탐에 유리했고 parallel은 경과 시간이 짧았다. 서로 다른 모델·생성 품질·큰 문서·A07 비기능 결함으로 일반화하지 않는다. 승인된 비공개 A05/A08 전체 고정 평가나 #20 통합 평가를 대신하지 않는다.

TC-F14 수용 증거: 실제 4개 가지에 barrier를 둬 동시에 진입함을 확인하고, A08을 지연시킨 뒤 타임아웃으로 실패시켜 A06의 정상 지적·나머지 3개 정상 호출·실패 A08 기록·불완전 표시가 함께 보존됨을 검증했다. 이 실패 주입은 stub 통합 검사이며 실제 API 장애를 재현했다고 표시하지 않는다. 실제 API 비교는 12조건 전부 완료, 30회 호출이며 강제 장애는 주입하지 않았다.

## A06 관계 문맥·키 의미 회귀 (#22, 2026-11-11)

#18에서 A06에 관계가 전달되지 않아 이미 존재하는 연결을 누락으로 지적하는 문제를 확인했다. A06 v4는 relationships를 입력에 포함하고, 관계로 생성되는 FK와 기본 키/추가 UNIQUE/복합 키의 계약 의미를 설명한다. 계약·팩·정답은 변경하지 않는다. v3 중간 검증에서 키에 is_unique=false라는 이유로 유일성 누락을 지적한 사례가 있어 키 의미를 추가했다. 정상 관계 지적을 줄이려던 A05 프롬프트 실험은 parallel 카디널리티 두 반복을 모두 놓쳐 되돌렸으며 A05 v1을 유지한다.

같은 합성 고정 설계 3종·두 방식·각 2회를 최종 프롬프트로 다시 실행했다. 12조건 모두 완료했고 A06의 관계 누락·키 유일성 오탐은 이 실행에서 0건이었다. [호출별 결과와 의미 대조](evidence/22-a06-context-regression-20261111.json)에 새 프롬프트와 기존 기대를 보존했다.

|---|---|---|---|---|---|
| parallel | 3/1 | 2 | 1 | 112,620/1,761 | 3.399 |

기본은 선정 해시에 대한 R1·R4 승인이다. 사용자가 R4 대기를 해제하고 R1 확정으로 대신하라고 명시한 경우에만 `approval_mode=r1_scoped_override`를 쓴다. `r1_override`에 동일 `subject_sha256`, `authorized_role=R1`, 실제 확정자, `replaces_role=R4`, `scope=this_selection_only`, 사유·지시 근거를 기록한다. R1 승인 하나와 확정자·근거가 일치해야 하며 R4 승인 항목을 동시에 넣을 수 없다. 해시가 바뀌면 재확정이 필요하고 일반적인 R4 승인 면제 설정은 두지 않는다. 결과 provenance·탐색 정책 해시에 예외 근거를 포함한다. 이는 R4가 검토했다거나 독립 평가를 마쳤다는 뜻이 아니다. 운영 팩·기존 결과·정답의 승인으로 확대하지 않으며 이름/FK 변경의 의미·불변성과 SQL 검증 결과는 별도로 기록한다.

### 탐색 조건의 전체 API 실행

`python -m specton.evaluation.run_pipeline CONDITION.json --out NEW_DIRECTORY --env-file LOCAL_ENV --pdf`는 승인된 사전 사본·입력·실행 조건의 해시를 고정하고 기존 API 그래프를 실행한다. 조건 파일에는 R1 확정자·근거와 전체 조건 해시가 필요하다. 매 노드에서 조건·사전·입력의 변경을 거절하며 운영 API의 기본 팩은 바꾸지 않는다.

`fresh_generation`은 원문에서 A01~A04를 새로 호출하며 고정 모델 파일을 받을 수 없다. 관측 후 확정한 이름 표현은 별도 A03 탐색 입력·프롬프트 버전으로 기록한다. `approved_model_replay`는 확정 모델을 재생해 이후 생성·검토·SQL 검증·승인·다운로드 연결을 확인한다. 재생 결과를 새 설계 생성이나 독립 평가 점수로 사용하지 않는다.

`without_domain_prompt_context`는 같은 원문·검증 정책을 유지하고 few-shot·도메인 팩 데이터·탐색 명명 힌트를 모델 요청에서 제외하는 대조다. 검증 팩 전체를 제거한 조건이 아니며 관측 후 탐색 대조로 보고한다. 원문의 기존 보조 분류 정보는 제거하지 않는다.

두 PDF 활성화 시 8종 산출물, manifest의 원문·모델·파일 해시, 승인본 다운로드 바이트를 검사한다. critical·실패 검토 가지가 있으면 자동 승인하지 않는다. 호출별 사용량·추정 비용·문서별 결과를 새 비공개 디렉터리에 남기며 기존 결과를 덮어쓰지 않는다. 의미 대응·최종 품질 채점은 별도이고 생성 완료만으로 통과 점수를 만들지 않는다.

그래프의 A04는 기존 속성을 재사용하는 FK의 NULL 충돌을 정리 단계로 전달한다. A04는 A03의 속성을 바꿀 수 없으므로 이 충돌을 출력 형식 재요청만으로 해결하지 않는다. 원래 속성·관계·재사용 선언을 유지한 채 정리기가 `invalid_fk_binding`을 검사하고 RULE-04·critical·`data_model` 재작업으로 연결한다. 정리 실패 시 산출물 생성과 승인은 계속 차단한다. 존재하지 않는 엔티티·속성·요구사항 참조나 잘못된 인용은 기존 출력 검사를 유지한다. A04 단독 호출의 사전 NULL 검사는 기본값으로 유지한다.
